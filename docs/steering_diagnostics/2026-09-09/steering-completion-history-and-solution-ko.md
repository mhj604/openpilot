# 급커브 완주 문제: 이전 시도 전체를 반영한 원인과 해결 방향

> 게시용 보관본. 작성 시점과 후속 정정을 구분한다. 최신 요약과 읽는 순서는 [기록 안내](README.md)를 참조한다. 원본 주행 데이터·화면·비공개 첨부는 로컬 보관이며 저장소에 포함하지 않는다.

작성일: 2026-09-09. 범위: 남아 있는 대화, Git 변경 이력, 8월 초기 실험 보고서, 9월 8일 저장 기록과 적용 소스의 분석. 새 주행·QA·차량 접속·설정 변경·펌웨어 변경·재부팅은 하지 않았다. 이전 자료를 수정하거나 삭제하지 않고 이 문서를 별도로 추가했다.

## 1. 결론부터

**지금 확인된 문제는 단순히 ‘C2가 더 꺾으라는 명령을 충분히 만들지 못한다’가 아니다. 실제 급커브의 핵심 구간에서는 허용 최대 명령이 CAN으로 송신되고 MDPS도 자동조향 활성 상태를 유지했지만, 핸들의 반응이 부족했다.**

따라서 Kp/Kf 증대, PID 전환, 140→180° 확대를 다음 완주 해법으로 권하지 않는다. 반대로 ‘MDPS 모터가 물리적으로 한계이므로 반드시 교체해야 한다’도 아직 증명되지 않았다. 외부 자동조향 요청에 대한 EPS 내부 제한·필터링, 조향계와 타이어 부하, 과도응답을 현재 데이터만으로 완전히 분리할 수 없기 때문이다.

하드웨어와 안전 한도를 유지하면서 개발할 가치가 있는 후보는 **실제 조향 응답을 고려하는 경로·명령 계획**이다. 다만 이는 사용할 수 있는 힘을 더 적절한 시점에 사용하는 방법이지, 힘을 새로 만드는 방법이 아니다. 같은 도로 안에서 실현 가능한 경로가 없거나 지속적으로 필요한 보조력이 현재 외부 조향 능력을 넘으면, 소프트웨어 보정만으로 자동 완주를 보장할 수 없다.

이전 답변의 ‘개별 응답 보정 + 사전 경고’는 개선 방향이지 완주 해결책이 확정됐다는 의미가 아니었다. **경고와 수동 인계는 안전 대응이며, 자동 완주 성공으로 세지 않는다.**

## 2. 차량·버전 전제

- 차량은 순정 SCC·레이더·전방 카메라가 없고 일반 크루즈가 있는 그랜저 IG 하이브리드다. C2 자체의 도로 카메라는 별개다.
- 기존 C-MDPS를 사용한다. 정확한 EPS 부품번호·펌웨어 식별 자료는 확보되지 않았다. ‘SCC가 없다’는 사실만으로 특정 MDPS의 내부 성능 수치나 고장을 단정하지 않는다.
- 9월 8일 기록의 C2 적용 커밋은 `4caf69d`다. Mac/Git의 `c19df14`와 다르다.
- 기록된 설정은 최대 요청 384, 증가/감소 제한 3/7, 각도 제한 140°, Torque 제어다.
- `openpilotLongitudinalControl=False`이며 해당 시험에서 가속·제동 요청은 0이었다. 일반 크루즈 버튼 제어를 직접적인 자동 브레이크 권한으로 취급하지 않는다.
- 저속개조·하드웨어 교체는 사용자가 제외한 범위다. 크루즈 메인 `---`에 따른 조향 on/off, 조향-only 상태에서 브레이크를 밟아도 조향 유지, WebUI 작업은 보존 대상이다.

## 4. 확정 우회전이 구분해 준 것

사용자가 정확한 시험이라고 확인한 것은 기록 시작 약 3분 31초대의 우회전이다. 초반 약 12초의 오류 구간이 아니다.

| --- | ---: | ---: | ---: | --- |

3:31.50~3:32.40 구간의 모든 송신 표본은 -384, 요청 비트 1이었다. 특히 3:32.00~3:32.30에는 최대 명령 중인데 핸들이 약 0.3°만 더 돌아갔다. 이후에는 56.2°까지 진행했으므로 영구적인 기계적 잠김이나 정확한 36° 고정 제한으로 표현하지 않는다.

전체 기록에서 수신한 LKAS 송신 확인 72,551개는 대응하는 송신 내용과 일치했고 거부 프레임은 없었다. 끝의 송신 하나는 기록 종료 경계에서 확인 프레임이 없었다. Panda의 송신 확인은 **CAN으로 내보냈다는 증거**이지 EPS가 요청 전체를 실제 물리 토크로 구현했다는 증거는 아니다. MDPS 활성·출력 보고가 그 이후 반응의 추가 단서다.

이 구간에서 우선순위가 내려간 설명:

- Panda가 명령을 계속 차단함: 해당 구간의 송신 증거와 맞지 않음.
- C2가 힘을 줄임: 핵심 연속 구간은 최대 명령을 유지함.
- 운전자가 먼저 개입해 감쇠됨: 큰 개입은 초기 부족 뒤에 발생함.
- 1.08 km/h 출력 중지·18 km/h 미만 적분 정지: 초기 부족 시 속도와 맞지 않음.
- 90° 지속 오류·140° 제한: 초기 각도는 약 36°이고 오류도 없었음.

반면 남는 설명은 **현재 외부 자동조향 경로의 응답이 해당 순간 필요한 조향을 따라가지 못함**이다. 요청 상한에 도달했다는 사실은 확정할 수 있지만, 그 안에서 EPS 내부 제한·응답 지연·노면 부하가 각각 얼마나 기여했는지는 확정할 수 없다.

384는 원시 CAN 요청값이지 Nm나 각도가 아니다. MDPS 출력 보고값 약 10~11도 단위가 명시되지 않아 모터의 최대 Nm로 쓰지 않는다. 제어기의 actualLateralAccel 역시 각도·속도·차량 모델 기반 추정값이다. 수동으로 더 돌린 최대 180° 또는 과거 수백 도는 늦은 회복 조향이 섞이므로, 정상 경로 완주에 처음부터 필요한 최소각으로 사용하지 않는다.

## 5. 완주하려면 동시에 충족해야 하는 조건

1. **힘:** 요청 가능한 범위 안에서 필요한 방향의 조향 응답을 만들어야 한다.
2. **시간:** 커브에 도착하기 전에 필요한 만큼 돌아가야 한다. 최대 힘이 충분해도 상승 시간·지연이 길면 늦는다.
3. **지속성:** 커브 끝까지 정상적인 요청과 EPS 동작이 이어져야 한다.
4. **경로:** 도로·차선 안에서 위 조건을 만족하는 경로가 실제로 존재해야 한다.

현재 기록은 1·2의 결합된 부족을 보여 준다. 다른 구간에는 90° 이상 지속 시 MDPS 오류가 있어 3도 별도 과제로 남는다. 초기 부족 하나를 고쳐도 큰 각도에서 끝까지 이어진다는 보장은 아직 없다.

## 6. 제안하는 소프트웨어 솔루션과 한계

### A. 게인 확대 대신 ‘실제로 따라갈 수 있는 경로’를 계획

현재 MPC는 위치·방향·곡률과 곡률 변화율을 다루지만, 384라는 명령 상한과 이 차량의 실제 MDPS 반응을 직접 예측하지 않는다. 따라서 수학적으로 경로가 나왔다고 실제 핸들이 그 속도로 움직일 수 있는 것은 아니다.

개발 후보는 다음 구성이다.

- 기존 저장 기록에서 실제 송신값과 핸들의 응답을 연결해 속도·회전각·이전 명령에 따른 응답 범위를 구성한다. 개입·오류·요청 해제 구간을 정상 자동조향 학습 자료와 섞지 않는다. 현재 한 번의 과도응답에서 전 영역 모델을 얻었다고 주장하지 않는다.
- 이 응답 범위와 기존 명령/증가율 제한을 앞경로 처리에 포함한다. 단순히 0.35초를 더 당겨 읽는 방식과 다르다.
- 충분한 도로 경계 정보가 있을 때만, 차선 안에서 필요한 조향 변화가 더 완만한 경로를 찾는다. 차선을 넘거나 커브 안쪽을 잘라 부족한 조향을 숨기면 안 된다.
- 필요한 경우 적절한 시점에 기존 허용 범위의 요청을 시작하고, 포화 이후 오차를 누적시키는 방향의 보정을 피한다. 운전자 우선·고장 차단·Panda 제한은 유지한다.
- 완만한 커브의 기존 동작을 전역 게인 변경으로 흔들지 않도록 적용 조건과 모델 신뢰 범위를 제한한다. 현재 자료로 모든 속도·좌우 방향에 대한 신뢰 범위를 확보한 것은 아니다.

**기대할 수 있는 효과:** 늦게 힘을 쌓거나 응답 능력을 과대평가한 경로 때문에 실패한 경우, 사용 가능한 조향으로 통과할 여지를 늘림.

**해결하지 못하는 경우:** 커브를 유지하는 데 필요한 힘 자체가 지속적으로 부족하거나, 도로 폭 안에 실현 가능한 다른 경로가 없는 경우. 이때 계획기를 더 복잡하게 만들어도 동일 조건 완주를 만들어낼 수 없다.

공식 comma 자료도 EPS 내부 평활화, 속도 의존성, 일부 EPS 펌웨어별 반응 차이를 설명한다. 이것은 차량별 응답을 다룰 근거이지 본 차량에서 효과가 입증됐다는 뜻이 아니다. [comma steering-control](https://github.com/commaai/comma-steering-control)

동적 제약을 포함하는 preview 연구는 이런 설계 방향을 뒷받침하지만, 해당 자료의 결과는 CarSim–Simulink 시뮬레이션이다. C2·비-SCC 그랜저의 바로 쓸 수 있는 완주 코드가 아니다. [Preview Control with Dynamic Constraints](https://pmc.ncbi.nlm.nih.gov/articles/PMC8347934/)

### B. 차량별 토크 환산·지연 보정은 A의 구성 요소

현재 TorqueMaxLatAccel에서 얻은 2.7을 이 차량의 실측 최대 성능으로 볼 근거가 없다. 개별 차량 반응과 맞지 않는 환산을 개선하면 상한에 이르기 전 필요한 명령을 더 정확히 만들 수 있다. 하지만 이미 송신이 384인 동안 같은 상한으로 더 큰 명령을 만들어내지는 못한다.

공식 torqued를 그대로 추가하는 것도 저속 급커브 해결을 보장하지 않는다. 현재 공식 구현은 일반 학습에서 15 m/s(54 km/h) 초과, 횡가속도 크기 1 m/s² 이하 등의 자료를 사용한다. 따라서 이번 25~30 km/h 최대 요청 구간을 직접 학습해 해결하는 구조가 아니다. [공식 torqued 소스](https://github.com/commaai/openpilot/blob/master/openpilot/selfdrive/locationd/torqued.py)

### C. 속도는 보조 조건이며 단독 해법이 아님

감속하면 같은 반경에서 필요한 횡가속도는 줄어들지만, 같은 좁은 경로를 도는 데 필요한 기하학적인 바퀴 각도까지 없어지지는 않는다. 극저속에서는 타이어 마찰 등 다른 부하의 상대적인 영향도 크다. 사용자가 2~8 km/h에서도 부족했다고 했으므로 특정 낮은 속도를 ‘완주 속도’로 지정하지 않는다.

기존 커브 속도 계산은 이번 핵심 시점에 약 46.8 km/h를 표시하는 계획값을 갖고 있었지만 실제로는 30~28.5 km/h에서도 부족했다. 이 계획값은 실제 ECU에 적용된 속도 명령이 아니다. 기존의 일반적인 커브 속도 식을 이 차량의 조향 능력으로 취급할 수 없다는 의미다.

현 구조에서 운전자가 종방향을 담당한다는 전제를 유지한다. ‘더 일찍 자동 감속하면 해결’이라고 말하면서 실제로 없는 브레이크 제어 권한을 가정하지 않는다. 사전 감속 안내는 제공 가능한 대응이지만 자동 완주 자체와는 별개다.

### D. 높은 각도에서의 지속성과 EPS 호환성은 별도 조건

현재 전체 기록에는 높은 각도에서 MDPS 오류가 나타난 다른 구간이 있다. 요청을 임의로 토글하거나 오류를 숨기는 것을 해법으로 삼지 않는다. 정확한 EPS에서 정상적으로 허용되는 조향 동작 범위를 설계에 반영해야 한다. 현재 그 범위 밖의 지속 조향까지 확보했다고 말할 수 없다.

소프트웨어만으로 더 큰 외부 조향 권한을 확보할 수 있는 제조사 승인 업데이트가 해당 EPS에 존재한다면 별도의 가능성이다. 그러나 지금은 EPS 부품번호·펌웨어가 없고 적용 가능한 공식 업데이트를 확보하지도 못했다. 다른 차종 EPS 펌웨어, SCC 유무만으로 선택한 코딩, 속도 신호 위조를 대안으로 권하지 않는다. 추후 필요 정보는 정차 상태의 정확한 EPS 식별과 정비 정보이지, 위험한 급커브를 다시 반복하는 것이 아니다.

## 7. 이전 제안 중 바로잡을 내용

- **‘당근의 409면 해결 가능’이라는 이전 단정은 철회한다.** 같은 차명·다른 fork의 숫자는 동일 EPS에서 안전하게 완주한 증거가 아니다. 384 포화도 안전 상한을 올려도 된다는 근거가 아니다.
- **‘384 포화가 아니다’라는 전 구간 일반화는 잘못이었다.** 일부 구간 최대 355와, 최신 확정 구간의 실제 384 연속 송신은 서로 다른 관측이다.
- **‘12초대 MDPS 오류가 사용자가 말한 급커브 원인’은 철회된 설명이다.** 확정된 3분 31초 구간의 초기 부족에는 오류가 없었다.
- **120°는 이미 시도했고, 140°도 적용했다.** 같은 변경을 아직 안 한 해결책처럼 제안하지 않는다.
- **전용 preview는 구현 이력은 있지만 독립 주행 결과를 확보하지 못했다.** ‘이미 실패’ 또는 ‘복원하면 성공’ 어느 쪽도 단정하지 않는다.
- **`c19df14`는 시험 당시 적용 버전이 아니다.** 안전 관련 미해결 사항도 있어 무조건 pull할 완주 솔루션으로 권하지 않는다.

**추천은 설정값 재조정의 반복을 멈추고, 실제 MDPS 응답을 포함한 경로 계획 설계로 문제의 초점을 옮기는 것이다.** 다만 결과물이 ‘이 경로는 현재 조향 권한으로 불가능하다’일 수 있다는 조건을 처음부터 명시해야 한다. 사용자가 원하는 것이 특정 급커브의 확실한 자동 완주라면, 현 시점에는 완료됐다고 말할 근거가 없다.

공식 openpilot도 급커브·교차로 등에서는 제한된 조향 토크로 의도한 동작을 하지 못할 수 있음을 명시한다. 현재 상태로 해당 커브를 장치에 맡기는 것을 권하지 않는다. [공식 제한 사항](https://docs.comma.ai/LIMITATIONS/)
