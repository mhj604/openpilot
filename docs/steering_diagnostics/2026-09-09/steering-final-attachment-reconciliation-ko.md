# 마지막 시험 전 분석과 실제 시험 후 분석의 통합 결론

> 게시용 보관본. 작성 시점과 후속 정정을 구분한다. 최신 요약과 읽는 순서는 [기록 안내](README.md)를 참조한다. 원본 주행 데이터·화면·비공개 첨부는 로컬 보관이며 저장소에 포함하지 않는다.

작성일: 2026-09-09. 실행 기준: C2 기록의 `4caf69deadb0f6a14691d09f80a941bd6b49da7b`.

## 최종 판단

**확정된 우회전의 초기 조향 부족은 ‘고각도 오류로 MDPS가 꺼짐’이 아니라, ‘허용 최대 조향 명령을 송신하고 MDPS도 활성 상태인데 실제 조향 반응이 부족함’이다. 다른 구간에는 고각도 오류와 조향 비활성화가 별도로 존재한다. 운전자 개입 뒤 140°를 넘으면서 발생한 C2 요청 해제도 이 둘과 구분해야 한다.**

따라서 하나의 90° 제한이나 하나의 튜닝값으로 전체 현상을 설명하는 결론은 유지할 수 없다. 현재 근거로는 다음 세 현상을 분리하는 것이 가장 정확하다.

1. **최대 요청 중의 반응 부족:** 확정 우회전의 주된 현상. 명령 포화는 관측됐지만 EPS 내부 제한·부하·과도응답의 기여는 미분리.
2. **고각도에서의 오류·비활성화:** 다른 구간에서 실제 관측. 해당 오류가 모든 급커브 부족을 설명하지는 않음.
3. **운전자 개입 이후의 host 각도 차단:** 확정 우회전 후반의 별도 사건. 초기 부족을 일으킨 선행 원인이 아님.

MDPS 모터가 고장 났거나, 모터의 물리적 최대 출력이 부족하거나, 하드웨어 교체가 필수라는 결론은 아직 낼 수 없다. 반대로 PID 교체·Kf 증가·선행 조향·오류 회피 기능만으로 완주가 가능하다는 결론도 낼 수 없다.

## 1. 분석 범위와 근거의 우선순위

이번에 읽은 첨부 문서는 마지막 시험 전에 작성된 버전 정정 및 원인 가설이다. 문서 안의 설정 변경 권고는 분석 대상으로 읽었으며 실행 지시로 취급하지 않았다.

- 첨부: `비공개 사용자 첨부/pasted-text.txt` 전체 291줄.
- 실제 실행 조건: 같은 폴더의 `metadata.json`.
- 실제 거동: `telemetry.jsonl.gz`에서 이미 만들어 둔 `decoded-recording.pickle`의 저장 표본을 다시 읽음.
- 적용 소스: 현재 체크아웃 내용으로 대신하지 않고 `git show 4caf69d:경로`로 Torque 제어기, 차량 제어기, 차량 상태 처리, CAN 생성, PID, Panda 소스를 읽음.
- 이전 이력: `steering-completion-history-and-solution-ko.md`와 그 근거로 정리한 초기 실험·대화·커밋.

우선순위는 사용자 확인이 있는 실제 구간 및 실행 조건 → 해당 버전 코드 → 다른 구간과 이전 실험 → 일반적인 공식 구현 → 시험 전 가설이다. 여러 답변이 같은 가설을 반복했다고 독립적인 실측 증거가 늘어나는 것은 아니다.

차량은 순정 SCC·레이더·전방 카메라가 없는 일반 크루즈 차량이라는 전제를 유지한다. C2 자체 카메라는 별개다. 정확한 EPS 부품번호·펌웨어는 기록에 없으므로 SCC 유무만으로 특정 EPS의 내부 성능을 추정하지 않는다.

## 3. 원본 기록이 가설의 순서를 바꾸는 이유

### A. 약 3:31.50~3:32.40 — 활성 상태의 최대 요청, 부족한 반응

저장된 약 0.9초 구간에는 MDPS와 송신 확인 프레임이 각각 90개 있었다.

- 송신 토크는 전부 `-384`, 요청 비트는 전부 1, 송신 측 fault-request 비트는 전부 0.
- MDPS active는 전부 1.
- MDPS fault, fail, unavailable, error는 전부 0.
- 운전자 토크 원시값은 -6~47, carState의 개입 표시는 False.
- MDPS 출력 보고값은 -11.3~-9.6. 단위가 명시되지 않아 실제 모터 Nm로 해석하지 않음.
- 핸들 각도는 약 32~38° 부근이며, 212.0→212.3초의 근접 동기 표본은 -36.4→-36.7°.
- 213.0초에는 -56.2°까지 더 움직임. 따라서 36°에서 영구적으로 잠기거나 정확히 그 각도에 고정 제한이 있다고 말하지 않음.

**이 조건은 ‘90° 이상에서 약 1초 뒤 발생하는 고각도 오류’ 가설이 요구하는 조건과 맞지 않는다.** 핵심 부족은 그 각도에 도달하기 전에 발생했다.

### B. 약 3:33.4 이후 — 운전자가 더 꺾음

23.5 km/h, 약 -76.6°에서 큰 운전자 토크와 개입 표시가 발생했다. 이후 수동 회복 조향이 섞인 최대 각도를 자동조향 성능이나 정상 경로의 최소 필요각으로 사용하지 않는다.

약 3:33.97, 21 km/h, -142.5°에서 최종 토크와 요청 비트가 0이 된다. MDPS active는 그 직후 내려간다. 해당 순간에도 MDPS fault/fail/unavailable은 0이다. 이는 `4caf69d`의 해당 속도 140° host 제한과 부합한다.

따라서 후반의 ‘명령 해제’를 앞선 ‘최대 명령 중 정체’의 원인으로 역전시키면 안 된다.

### C. 다른 구간 — 실제 고각도 오류

전체 기록에는 MDPS fault/fail이 켜지는 사건이 8번 있었다. 시작 시점의 핸들 각도 크기는 모두 90°보다 컸고, 자동조향 비활성도 관측됐다. 예를 들어 약 12.57초에는 2.5 km/h·124.7°, 440.21초에는 24.5 km/h·133.2°였다.

하지만 초반 구간은 사용자가 정확한 급커브 시험이 아니라고 구분했다. 다른 사건 대부분에는 운전자 개입 등이 섞여 있다. 이 사건들로 확정 시험의 초기 부족 원인을 덮어쓰지 않는다. 정확한 EPS 내부 오류 조건도 제조사 자료 없이 완전히 규명했다고 말하지 않는다.

공식 Hyundai 구현에는 90° 초과 지속 요청에 대한 EPS 오류 설명과 그보다 앞선 요청 관리가 존재한다. 이는 고각도 사건을 해석할 근거지만 모든 각도에서의 부족을 설명하는 근거는 아니다. [공식 Hyundai 차량 제어기](https://github.com/commaai/opendbc/blob/master/opendbc/car/hyundai/carcontroller.py)

## 4. 한 번 더 따져본 해석의 함정

### 4.1 ‘Panda 차단 없음’과 ‘요청 상한에 여유가 있음’은 다름

Panda가 프레임을 버리지 않아도, 제어기가 허용 상한 384까지밖에 요청하지 않는 상태일 수 있다. 이번에는 실제로 그렇게 상한에 붙었다. 따라서 ‘Panda가 거절하지 않았으니 384 제한과 무관’이라는 결론은 틀리다.

그러나 384를 넘어도 된다는 근거 역시 아니다. 프레임의 성공적인 CAN 송신은 EPS가 그 요청을 어떤 물리 출력으로 구현했는지까지 증명하지 않는다.

### 4.2 ‘오류 없음’은 ‘무제한 출력’이라는 뜻이 아님

EPS는 고장 없이도 외부 요청을 제한하거나 평활화할 수 있다. 반대로 active=1과 낮은 출력 보고값만으로 특정 내부 토크 상한을 확정할 수도 없다. 현재 남는 것은 **허용된 요청 아래에서의 실효 응답 부족**이며, 이를 물리 모터 한계와 동일시하지 않는다.

공식 comma 자료도 명령의 EPS 내부 평활화, 속도 의존성, 일부 EPS 펌웨어별 반응 차이를 설명한다. [공식 조향 응답 자료](https://github.com/commaai/comma-steering-control)

### 4.3 ‘C2 일반 오류 표시 없음’과 ‘원본 EPS 오류 없음’도 다름

`4caf69d`의 carstate.py는 `ToiUnavail` 누적을 임시 조향 오류 판정에 사용한다. 실제 다른 8개 사건에서는 fault/fail이 켜져도 unavailable은 0, 일반 steerFault도 False였다. 따라서 첨부 문서의 unavailable/fault를 서로 바꿔 쓸 수 있는 하나의 표시로 읽으면 안 된다.

확정 우회전은 일반 오류 표시만 본 것이 아니라 **원본의 fault/fail/unavailable/error 모두 0**인 구간이다. 이 차이 때문에 해당 초기 부족에서 고각도 오류 설명을 제외할 수 있다.

### 4.4 작은 횡가속도와 쉬운 조향은 동일하지 않음

저속에서 같은 곡률의 횡가속도 요구가 작아진다는 식은 맞다. 그러나 같은 좁은 경로를 돌기 위한 기하학적 바퀴 각도는 여전히 필요하고 타이어·조향계 부하가 사라지는 것도 아니다. ‘2~8 km/h에서도 부족 → 고각도 오류가 확정’은 성립하지 않는다.

이번 확정 구간은 25~30 km/h여서 1.08 km/h 출력 중지와 18 km/h 미만 적분 정지가 직접적인 차단 조건이 아니었다. 별도의 2~8 km/h 경험에 대해서는 이 기록의 원인 순위를 그대로 복제하지 않는다.

### 4.5 최대 요청 관측만으로 ‘더 일찍 보내도 반드시 실패’까지는 모름

211.0초의 원요청은 -384였지만 최종 송신은 -236, 211.5초에는 -384였다. 앞 구간에는 host의 명령 변화율 제한 등이 관여할 수 있는 시점 차이가 존재한다. 이는 더 적절한 시점 계획을 검토할 이유이지, 현재 시점 계획이 틀렸다거나 선행하면 완주한다는 증거는 아니다.

반대로 0.9초의 최대 요청 구간과 0.3초의 작은 각도 변화만으로 영구적인 최대 조향각이나 정상상태 최대 보조력 곡선을 얻었다고 말해서도 안 된다. 초기 정적 실험도 서로 다른 조건과 오류·중단을 포함해 이 간극을 완전히 메우지 못한다.

### 4.6 코드 버전과 Panda 바이너리 버전은 별도

메타데이터로 C2 소스 커밋 `4caf69d`는 식별됐다. Panda 서명 해시도 보관돼 있으나 이번 작업에서 특정 소스로 만든 바이너리와의 대응을 새로 확정한 것은 아니다. 따라서 Panda의 설명은 해당 소스와 관측된 송신 사실을 구분한다. 이번 핵심 명령이 실제 송신됐다는 관측은 그 별도 버전 문제와 무관하게 남는다.

| 같은 우회전 후반의 해제 | 운전자 개입 뒤 host 각도 제한으로 요청 해제 | 기록과 해당 코드가 부합 |
| 다른 구간의 끊김 | 큰 각도에서 MDPS fault/fail 및 비활성화 발생 | 오류 발생은 직접 관측, 정확한 내부 조건은 추정 |
| 지속적인 Panda 송신 거절 | 확정 시험의 원인으로 지지되지 않음 | 실제 송신 근거와 불일치 |
| Kf 부족·라이브 튜닝 초기화 | 확정 시험의 직접 원인으로 지지되지 않음 | 당시 설정·최대 송신과 불일치 |
| MDPS 고장·물리적 최대 출력·교체 필수 | 확정 불가 | 필요한 식별·부하·물리 출력 근거 없음 |

## 6. 해결 방향에 대한 최종 결정

### 지금 권하지 않는 변경

- Kf=11, 일반 PID로 변경, Ki 증대로 이번 문제를 해결하려는 처방.
- 140→180° 변경을 초기 정체 해결책으로 삼기.
- 고각도 오류 회피 토글을 켜면 전체 문제가 해결된다고 기대하기. 이 분기는 기존 각도/기어 조건과도 동작 차이가 있어 단순한 무해한 토글로 취급하지 않는다.
- Panda 최대 요청·변화율·운전자 우선 보호를 완화하기.
- `c19df14`를 이번 시험의 기준 또는 완주 패치로 적용하기.

### 남아 있는 개발 후보

직전 답변에서 제안한 **실제 조향 응답을 반영한 경로·명령 시점 계획**은 기존 능력을 더 잘 활용하기 위한 후보로 유지한다. 하지만 그것은 원인이 ‘계획기’로 확정돼 나온 처방이 아니다. 해당 응답 모델과 도로 경계 안에서 실현 가능한 경로가 아직 확보되지 않아, 즉시 구현·배포할 완주 해법으로 승격하지 않는다.

완주에는 작은 각도부터 필요한 반응이 나오는 것과 큰 각도에서도 정상 동작이 이어지는 것이 모두 필요하다. 어느 한쪽만 다루는 수정은 전체 해결이 아니다. 현재 차량에는 C2가 직접 제동해 진입속도를 보장하는 기능도 없으므로 자동 감속을 당연한 전제로 넣지 않는다.

정확한 EPS 부품번호·펌웨어에 적용할 수 있는 제조사 승인 소프트웨어 대응이 존재한다면 별도 가능성이지만, 현재 그 자료는 확보되지 않았다. 다른 차종 펌웨어나 저속개조는 범위에서 제외한다.

**최종 결론: ‘MDPS 외부 자동조향 경로의 실효 반응 부족’과 ‘별도의 고각도 오류/후반 host 차단’이 함께 존재한다. 초기 부족을 90° 오류 하나로 설명하는 첨부의 1순위 가설은 마지막 시험으로 수정돼야 한다. 하드웨어 고장이나 교체 필요가 확정된 것은 아니며, 현 권한을 유지하면서 같은 급커브를 반드시 자동 완주시키는 소프트웨어 처방도 아직 확정되지 않았다.**

## 작업 결과와 제한

Search 스킬은 공식 구현 1건과 제작자의 조향 응답 자료 1건을 직접 읽는 데 사용했다. 새로운 광범위 검색이나 외부 QA는 하지 않았다. 공식 일반 동작보다 이 차량의 실제 각도·원본 오류 비트·송신 기록을 우선하는 판단에 활용했다.

첨부나 이전 보고서를 고치거나 지우지 않았다. 이 문서만 새로 추가했다. 차량 접속, 코드·Params·펌웨어 변경, 재부팅, 신규 주행, 빌드·QA는 수행하지 않았다. 추가 주행 없이 가능한 결론과 아직 모르는 부분을 구분한 분석이며 차량 적용 승인이 아니다.
