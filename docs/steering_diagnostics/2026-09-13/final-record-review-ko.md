# 이전 주행 기록 재분석: 저속 급커브의 해결 범위

2026-09-13. 새 주행이나 제어기 실행 없이 기존 원본 두 개를 다시 읽었다.

## 최종 결론

**앞서 ‘차량별 저속 토크 보정’을 가장 유력한 성능 개선 후보로 제시했지만, 기존 실패 구간의 원본을 다시 집계한 결과 이를 우선 적용할 근거는 부족하다.** 가장 강한 기록에서는 이미 계산 상한에 도달했고, 한 구간에서는 실제 송신도 계속 상한이었다.

따라서 현재 자료로 제시할 수 있는 정확한 답은 다음과 같다.

- 기존 최대 명령·같은 도로 경로·현재 조향 부하를 유지하면서, Kp/Kf·마찰·적분 보정만으로 해당 급커브를 완주시킨다는 소프트웨어 해법은 확보하지 못했다.
- 최대 명령 전의 응답 정확도 개선과 최대 보조력 부족 해결은 다르다. 전자를 후자의 해결책으로 포장하지 않는다.
- 다음 근본 원인 조사 대상은 이 차량의 **정확한 EPS 사양에서 허용된 외부 보조력이 무엇인지, 그것을 정상적으로 사용하고 있는지**다. 해당 식별 정보가 없는 상태에서 차량별 계수·코딩·업데이트를 처방하지 않는다.
- 고각도 MDPS 오류 중단은 별도 문제다. 실제 오류 반영은 필요하지만, 오류를 인지하도록 고친 것을 완주 성능 개선으로 부르지 않는다. 보호 타이머 회피나 보호 제한 완화는 제외한다.

‘반드시 해결하는 값’을 임의로 만들어 제시하는 대신, 기존 자료가 지지하는 범위까지 결론을 제한한다.

## 1. 명확한 실패 구간에서 요청 여력이 있었는가

### 9월 8일: 오류 없이 덜 꺾인 사용자 확정 우회전

구간은 캡처 시작 211.5~212.4초다. 초반 12초 구간이 아니다.

| 항목 | 원본 재집계 |
| --- | --- |
| 연결한 표본 | 90개 |
| 속도 | 27.0~30.0 km/h |
| 실제 조향각 | -31.7~-37.6° |
| 계산 명령 | 90개 모두 -384 |
| 실제 송신 확인 | 90개 모두 -384 |
| MDPS 상태 | 활성, fault/fail/unavailable/error 없음 |
| 운전자 토크 크기 | 원시값 최대 47, 큰 개입 표본 제외 조건 충족 |
| MDPS 출력 보고값 크기 | 중앙값 10.4, 범위 9.6~11.3; Nm 아님 |

| 연결한 메시지의 최대 시각 차이 | 약 18.2 ms |

**판단:** 이 구간은 게인이 작아서 최종 명령을 덜 보낸 상황이 아니다. 속도도 18 km/h보다 높으므로 극저속 적분 동결을 초기 부족의 원인으로 지목할 수 없다. 상한을 유지하는 한 계산 보정을 크게 해도 이미 나온 -384보다 더 큰 명령을 만들 수 없다.

표의 짧은 구간 이후 실제 각도는 더 증가했으므로 ‘36°에서 기계적으로 잠겼다’고 표현하지 않는다. 외부 자동조향 응답이 당시 필요한 회전을 따라가지 못했다는 결론이다.

### 9월 9일: 실제 MDPS 오류가 발생하기 직전

사용자가 사진으로 확정한 우회전의 155.0~157.15초를 별도로 집계했다. MDPS 오류는 그 직후 약 157.155초에 발생했다.

| 항목 | 메시지 시각 차이가 30 ms 이하인 표본 |
| --- | --- |
| 표본 수 | 162개 |
| 속도 | 14.0~18.0 km/h |
| 계산 명령 크기 | 155개에서 상한 384, 나머지 약 293~384 미만 |
| 실제 송신 크기 | 264~384, 중앙값 345 |
| 제한 적용 표시 | 153개 |

| 적분 항 | -0.0345로 유지 |

**판단:** 적분이 멈춰 있었지만 계산 명령은 이미 대부분 상한이었다. 실제 송신이 더 작은 것을 전부 ‘C2가 힘을 덜 쓰는 튜닝 오류’로 해석하면 안 된다. 운전자 토크 기반 제한과 변화율 제한, 그 이전 상태의 영향이 함께 있다. 각 표본에서 제한 원인을 하나씩 완전히 분해한 집계는 아니다.

이후 MDPS 오류가 발생한 구간에서는 출력이 감소했다. 오류 이후의 작은 명령을 정상 조향의 사용 가능한 여력으로 분류하지 않았다.

## 2. 2–8 km/h에 보정 후보가 남아 있는가

전체 기록에서 다음 조건의 표본을 선별했다.

1. 기록 유효성·차량 CAN 유효성이 참이고, OP 및 조향 제어가 활성.
2. 송신 요청 활성, 별도 전환 요청 없음, MDPS 활성 및 원본 오류 비트 모두 0.
3. 큰 운전자 개입 표시 없음, 운전자 토크 원시값 절댓값 50 이하.
4. 연결 메시지 시각 차이 30 ms 이하.
5. 지연 정렬된 제어기 오차를 속도의 제곱으로 나눈 크기가 0.003 이상이고, 송신 방향이 그 오차를 보정하는 방향.
6. 계산값이 상한의 90% 미만이며 송신과 계산값 차이가 4 이내, 제한 적용 표시 및 일반 오류가 없음.

5·6번은 **뚜렷한 계산상 여력 후보를 찾기 위한 분석 기준**이다. 차량 제어값이나 권장 설정이 아니며, 실제 도로에서 요구되는 조향을 정확히 측정한 기준도 아니다. 지연된 제어기 오차에는 모델·속도 변화의 영향이 있다.

| 캡처 | 2~8 km/h 미만에서 조건 충족 표본 | 실제 각도 | 계산 명령 크기 | 연속 조건 충족 표본의 최장 시간 범위 |
| --- | ---: | --- | --- | ---: |
| 9월 8일 | 16개 | 약 -5.9~+5.8° | 약 79~173 | 0.07 s |
| 9월 9일 | 11개 | 약 +15.7~+17.6° | 약 213~226 | 0.03 s |

8~18 km/h에서는 위 조건을 모두 충족하는 표본이 두 기록 모두 0개였다. 이것은 이 속도에서 개선 여력이 절대로 없다는 뜻이 아니라, **이 조건과 저장 범위에서 뚜렷한 후보를 확보하지 못했다는 뜻**이다. 90% 이상인 부분 요청이나 선별 기준 아래의 작은 오차를 조사에서 없었던 것으로 취급하지 않는다.

2~8 km/h의 후보들은 작은 각도의 짧은 구간이었으며, 사용자가 실패로 확정한 큰 우회전은 아니다. 후보 시간이 짧다는 것도 선별된 표본의 연속 범위이지, 실제 현상이 반드시 그 시간만 지속됐다는 의미가 아니다.

**판단:** 기존 극저속 자료만으로 ‘저속 토크 환산을 이렇게 바꾸면 급커브가 완주된다’는 수치나 모델을 만들기 어렵다. 같은 방향의 지속적인 부족, 충분한 각도·부하 범위, 비교 가능한 정상 응답이 부족하다.

## 3. 화면에 경고가 없었던 이유와 관련 설정

현재 소스의 포화 경고는 36 km/h 초과 등 조건에서만 누적된다. 그래서 9월 8일의 90개 최대 송신 표본에서도 포화 표시가 False였다. **포화 표시가 없다는 것은 최대 명령이 아니라는 증거가 아니다.** 이 조건은 표시 해석이며 토크 상한을 낮추는 원인으로 혼동하지 않는다.

측정 당시의 Torque Kp/Ki/Kf 저장값은 10/1/10, Friction 65, MaxLatAccel 27, LiveTune OFF였다. 단위가 서로 같지 않은 저장값이다. `4caf69d`에도 속도별 P·마찰 보정이 있었으므로, 현재 코드에 저속 보정이 전혀 없어서 생긴 문제라고 할 수 없다.

최신 Torque 코드 전체를 복사하거나 PID로 바꾸는 것이 최대 외부 보조력을 늘리는 것도 아니다. 공식 [조향 응답 자료](https://github.com/commaai/comma-steering-control)는 차량별 비선형 관계를 설명하지만, 허용 출력을 초과하는 힘을 만들어 주는 기술은 아니다.

## 4. 정확한 해결 경로와 아직 처방할 수 없는 부분

### A. 단순 튜닝은 우선 해법에서 제외한다

실패 구간에 계산 상한 도달 증거가 있으므로 Kp/Kf·마찰·적분 상향을 우선 처방하지 않는다. 기존 정상 경로의 정확도 개선 가능성까지 부정하는 것은 아니지만, 그것을 이번 실패의 직접 해결책으로 볼 자료가 없다.

초기 정차 자료의 요청 320·384에서 출력 보고값 중앙값이 비슷했던 사실도 같은 방향의 단서다. 서로 다른 조건의 시험이고 물리 단위가 미확정이므로 공장 상한이 정확히 320이라고 선언하지 않는다. 명령이 전달돼도 실제 출력이 증가하지 않는 상단 영역을 구분해야 한다는 [개발자 설명](https://github.com/commaai/openpilot/pull/25866)과 함께 해석한다.

### B. 출력 정체의 근본 대응은 정확한 EPS 사양 식별부터다

두 캡처의 `eps_firmware_hex`는 모두 빈 목록이었다. 즉, 현재 보고서는 장착된 EPS의 정확한 펌웨어 버전을 갖고 있지 않다. 이전 부품 조사의 M9000/M9050은 후보였고 실제 장착품이 확정된 것이 아니다.

다음 조사에 필요한 것은 **현재 장착된 컨트롤러 부품번호와 소프트웨어 식별값**이다. 기존 라벨·정비 내역·진단 기록처럼 새로운 위험 주행 없이 확보할 수 있는 정보가 우선이다. VIN이나 인증 정보를 공개 저장소에 올릴 필요는 없다.

그 식별 정보로 제조사가 허용한 외부 조향 사양, 현재 구성의 적합성, 적용 가능한 정상 업데이트 또는 보정이 있는지를 구분할 수 있다. 그런 정상적인 차이가 실제로 발견된 경우에만 그 차이를 바로잡는 구체적인 해결안을 낼 수 있다. 현재는 해당 업데이트·코딩을 확보하지 못했으므로 존재한다고 약속하지 않는다.

이 방향은 하드웨어 교체 권고나 보호 제한 해제 제안이 아니다. MDPS 오류가 없다는 사실만으로 타이어·기계 부하·전원 상태 등 모든 정상 여부가 입증된 것도 아니다. 그렇다고 근거 없이 특정 부품이나 공기압을 처방하지 않는다.

### C. 정상 한도 자체가 부족하다면 계산만으로 같은 조건을 완주시킬 수 없다

현재 사용 가능한 최대 보조력 자체가 해당 경로·부하에서 필요한 힘보다 작다면, 같은 경로와 한도를 유지한 채 요청값 계산만 바꿔 해결할 수 없다. 도로 경계 안에 기존 능력으로 가능한 경로가 존재하는 경우에만 경로 계획 개선이 후보가 된다.

이번 교차로는 경계 추정의 신뢰도와 필요한 최소 각도가 확정되지 않았다. 그러므로 ‘차선을 더 넓게 쓰면 된다’, ‘더 빨리 들어가면 된다’, ‘더 늦게 개입해 보라’는 방식은 권하지 않는다. 이 차량에 직접 OP 가감속 권한이 없는 전제도 유지한다.

### D. 고각도 중단은 별도의 오류·운용 범위 문제다

약 105° 부근의 MDPS 오류를 없었던 것으로 만들거나, 요청을 조작해 보호 타이머를 회피하는 패치는 제공하지 않는다. 실제 오류가 C2에 누락되는 부분은 안전 보완 대상으로 남지만, 이 보완을 커브 완주 해법으로 부르지 않는다.

## 5. 이전 제안을 어떻게 수정하는가

| 이전 제안 또는 해석 | 이번 원본 분석 뒤 판단 |
| --- | --- |
| 저속 토크 환산·마찰 보정을 우선 성능 개선 후보로 제시 | 조건부 연구 후보로 낮춘다. 실패 구간의 직접 근거가 부족함 |
| 적분이 동결되니 저속에서 부족할 수 있음 | 가능한 일반 설명이지만 이번 상한 구간의 직접 해법 아님 |
| 송신이 384보다 작으면 남는 힘이 있음 | 틀린 일반화. 운전자·변화율 제한과 오류를 먼저 분리해야 함 |
| 경고가 없으면 포화가 아님 | 저속에서는 성립하지 않음 |
| 최신 코드나 고각도 토글을 적용하면 해결 | 효과·차량 적합성을 확보하지 못했고 보호 회피도 제외함 |
| 지금 완주 가능한 설정값을 제공 | 근거가 없어 제공하지 않음 |

**최종 권고:** 추가 튜닝 적용은 보류한다. 이미 확보한 최대 명령·출력 정체 증거를 기준으로 EPS 식별과 정상 사양의 차이를 좁히는 것이 다음 근본 조사 단계다. 제어 표시를 고치거나 다른 게인을 적용한 뒤 ‘해결 완료’라고 보고하지 않는다.

## 방법과 한계

- [집계 도구](../../../tools/steering_diagnostics/summarize_request_headroom.py)는 저장 파일만 읽고 표준출력으로 집계를 낸다. 차량 연결·CAN 발행·제어기 실행·시뮬레이션·파일 쓰기를 하지 않는다.
- [집계 결과](request-headroom-summary.json)는 두 번의 출력 결과를 하나의 JSON 배열로 보존한 자료다. 주행 영상·위치·전체 파라미터 원본은 포함하지 않는다.
- 근접 메시지 연결은 30 ms 이내로 제한했다. 초과 표본은 9월 8일 809개, 9월 9일 11,899개였다. 특히 두 번째 기록의 공백을 정상 동작으로 메우지 않았다.
- 이 집계는 개별 ECU 내부 수신 시점의 측정이 아니다. CAN 송신 확인은 물리적 토크 측정과 다르다.
- 표본은 독립 실험 횟수가 아니며 비율을 전체 주행의 시간 비율로 해석하지 않는다.
- 원본은 그대로 보존했다. 새로운 주행·차량 접속·코드 실행 시험·테스트·QA는 하지 않았다. 데이터 집계만 수행했다.
- 이번 커밋은 문서와 오프라인 집계 도구 보존이며, 실제 조향 동작을 바꾸는 패치가 아니다. C2 pull·재부팅을 요청하지 않는다.
